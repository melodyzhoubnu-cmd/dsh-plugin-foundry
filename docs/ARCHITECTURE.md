# 建设繁荣的插件生态：分发、计量与支付

> 版本：v11.6 · 2026-11-06
> 宿主：DeepSeek Harness 0.2.2-rc.1（插件 engines 兼容 ≥0.2.1-rc.5）
> 状态：P1/P2 已实现，token 计量与可选上报已接入
> 变更：v11.6 §1.5 demo 改为病案编码质控（dsh-icd-rule-check），替代销售表 demo；v11.5 §0.3 增补落地顺序（token 分成先行，支付与交易基建后做）；v11.4 简化 §3.4 为「商店支付基座 + 开源平台最小集」；v11.3 交易改为轻量方案；v11.2 应用商店调研与结论其六；v11.1 新增 §2.6 防滥用与结算风控、结论其五；推荐在回合末尾有可见卡片；多索引 + npm/GitHub 按需 + 模型搜索触发

---

## 摘要

一个插件生态是否繁荣，不取决于目录里有多少条目，而取决于三件事能否同时成立：开发者愿意持续投入、插件能被需要它的人用上、投入能获得可计量的回报。DSH 生态已有 35,000 个插件，供给不再稀缺；短板在需求侧的分发效率，以及供给侧的收益闭环。

收益可以有三种形态：

1. **按 token 消耗分成或返点**：用户为模型调用付费，平台按插件归因的 token 把收入分给开发者，或按消耗量返还 token 配额；
2. **开发者自收费**：一次性购买、订阅、按次/按席位付费，由开发者自己收款；
3. **交易型插件**：开发者在插件里卖商品或服务，平台只展示，不参与交易。

三种形态都依赖于同一个前提：插件能被分发出去。没有分发，分成没有基数，自收费没有订单，交易没有成交。因此本文把问题拆成三个支柱：

- **在对话内与工作过程中的分发**：能力在任务需要时出现，而不是在用户不看的第二屏幕；
- **分布式 token 计量**：任何渠道进入的插件，其 token 消耗都可归因、可上报；
- **支付与交易基建**：开发者自收费与自营交易有位置可放，平台不碰资金、不担保。

三者合起来，构成生态飞轮的基础设施。

## 0. 生态视角

### 0.1 生态飞轮

```
开发者 ──发布──► 插件 / 能力 ──分发──► 用户使用
   ▲                                     │
   │              ┌──────────────────────┼──────────────────────┐
   │              ▼                      ▼                      ▼
   │        token 消耗            开发者自收费            开发者自营交易
   │              │                      │                      │
   └─ 平台分成 ◄──┘               开发者直收              开发者直收
```

开发者投入、用户使用、收益回流，三个环节缺一不可。平台只从 token 分成里取得收入，另外两条路径由开发者自己收款。

### 0.2 三个前提

| 前提 | 现状 | 要补的东西 |
|---|---|---|
| 开发者愿意持续投入 | 能看到下载量，看不到真实使用 | 可核对的使用量与收入 |
| 插件能被需要它的人用上 | 市场是拉式的，任务里看不见 | 对话内与工作过程中的分发 |
| 投入能获得可计量回报 | token 按请求计费，不按插件计费 | 计量、归因、上报、结算 |

三个前提不是并列的功能清单。分发是入口，计量是依据，支付与交易是出口。

### 0.3 三个支柱

| 支柱 | 解决的问题 | 对应章节 |
|---|---|---|
| 对话内与工作过程中的分发 | 用户看不见、选不对、装完用不上 | 第 1 章 |
| 分布式 token 计量 | 用量记不下来、归因对不上、上报不可信 | 第 2 章 |
| 支付与交易基建（本 demo 未实现） | 开发者自收费没有轻量路径，交易责任不清 | 第 3 章 |

三个支柱有先后：**先 token 分成，后支付与交易基建**。

- token 分成不需要新的收银台：用户已经在为模型调用付 token 费用，插件收入从这笔账单里分出来，平台只要把计量、归因、对账做对，就能先跑起来；
- 支付与交易依赖外部条件：渠道（Stripe、Paddle、x402）、开发者自己的商户与税务资质、退款与争议流程，这些不是平台能独立完成的；
- 所以先用真实用量验证「插件值得付费」，再把愿意单独付费的供给接进来。收银台可以后建，计量不能等。

## 1. 分发：对话内与工作过程

### 1.1 三个断点

| 断点 | 表现 | 后果 |
|---|---|---|
| 看不见 | 任务进行中，用户不知道有插件能帮上忙 | 用内置方法凑合，或根本不知道有更优路径 |
| 选不对 | 同类太多，质量、兼容性、来源不透明 | 推荐像广告，用户干脆不选 |
| 用不上 | 装完模型不知道，用户也忘了 | 安装量不等于使用量 |

用户正在改一份 xlsx，想按月份做趋势图。他不太可能停下来，打开市场，搜索「图表」，比较五个插件，再回来。更常见的情况是：他用内置方法凑合做完，或者根本不知道有更省事的路径。

市场是拉式的。它假设用户知道自己在找什么，也愿意离开任务去找。任务中的需求不是这样发生的：需求是隐性的，用户自己都说不清缺什么。

### 1.2 现有做法为什么不够

| 做法 | 解决什么 | 没解决什么 |
|---|---|---|
| 市场 / 目录 | 浏览、搜索、分类 | 用户要先离开任务；不解决「此刻需要什么」 |
| 榜单 / 评测 | 帮用户判断质量 | 静态；和当前任务无关 |
| 检索工具 | 模型主动找插件 | 模型要先意识到该找；没有 UI 和回执 |
| 安装器 | 把插件装上 | 装完模型不知道；用户不知道装了什么 |

这些做法各自解决一段。没有产品同时做到：在任务里发现、在授权内安装、装完有回执、模型下一步能用。

把缺口拆开，机会可以分成四类：

| 类型 | 定义 | 触发方式 | 信号 |
|---|---|---|---|
| 补缺 | 所需能力不存在 | 被动或主动 | 工具失败、缺依赖 |
| 升级 | 内置能做，但插件更好 | 主动 | 质量要求高、重复绕行 |
| 发现 | 用户不知道更优路径 | 被动或主动 | 主动询问、陌生领域 |
| 配方 | 一类任务需要一组能力 | 主动 | 任务类型识别 |

### 1.3 官方底座：统一上报协议、计量与结算、冷启入口

开发者可以自己做一个推荐插件，界面、排序、卡片都能做。但有三样东西只有官方能给：

1. **统一的上报协议**。DSH 里会同时存在市场、第三方分发器和插件自带的统计。如果每家定义一套 usage 事件、收据和批次格式，数据无法合并，也无法对账。官方提供一套公开 schema：`UsageEvent`、`Receipt`、`Batch`、`Settlement`；所有插件和分发器按同一格式上报。宿主天然能看到所有工具调用，这是单个插件没有的观察面，也是统一协议能成立的前提。
2. **计量与结算**。token 账单、归因、分成需要一个中立运营方。计量协议、验证器和结算适配器都开源，第三方可以复算、校验、接入；官方只运行参考实现，不把接口做成私有。
3. **冷启入口**。推荐插件自己要先被安装，这是启动悖论。官方入口可以先于任何插件存在，并在用户第一次进入工作区时完成一次授权。第三方分发者可以读取授权结果，但不能绕过官方 UI 扩大范围。

这三样都是协议和运行位置，不是界面功能。开源范围包括能力索引 schema、事件与机会协议、计量收据、结算适配器和参考实现。任何分发者都可以按同一套协议接入。

冷启授权由客户端本地弹窗完成，不接官方 onboarding，也不写入官方冷启流程。它问两件事：安装策略四选一（全部自动安装 / 仅官方精选自动安装 / 始终不自动安装 / 关闭推荐功能）；用量上报二选一（纯本地 / 上报用量，可帮助插件开发者获取收益）。默认始终不自动安装、纯本地。

触发方式有两种：

| 方式 | 触发 | 用户感受 | 授权 |
|---|---|---|---|
| 被动 | 用户问「有没有工具」「能不能做」；工具失败、缺依赖 | 回答里顺带给出能力与安装选项 | 超出授权时询问 |
| 主动 | 旁路在任务中发现升级或发现机会 | 不打断；在回合边界或错误点出现 | 仅限预授权范围 |

两种方式都不要求用户离开任务去市场。市场只承担浏览和深链。

分发方案的特征：

- 发生在对话内和工作过程中，不要求用户去市场；
- 被动和主动两种触发；
- 静默时 0 token，触发时约 40–100 token，只追加到请求尾部；
- 预授权范围内静默，范围外询问；
- 安装结果写进对话，不阻塞当前回合；
- 底座开源，允许多个分发者。

### 1.4 旁路架构：一种实现设想

下面的架构是一种实现设想。排序、交互、bundle 都可以换，只要保留三件事：旁路感知、预授权、对话内说明。

```
┌──────────────────────────────────────────────────────────────┐
│ ① 用户任务 / 对话                                             │
│    会话事件：消息 · 工具 · 文件 · 错误                        │
└──────────────────────────┬───────────────────────────────────┘
                           │
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ ② 能力旁路 Sidecar（宿主侧，静默时 0 token）                  │
│   观察者 → 任务画像 → 推荐引擎 → 机会                        │
│   召回 → 排序 → 净值；推荐对象：插件 / bundle                 │
│   触发：被动（询问/失败）· 主动（机会/轮次边界）              │
└──────────────────────────┬───────────────────────────────────┘
                           │ 机会（gap / uplift / discovery / recipe）
                           ▼
┌──────────────────────────────────────────────────────────────┐
│ ③ 预请求授权 + 投递门控                                       │
│   consent（全部 / 官方精选 / 不自动 / 关闭）· 预算 · 去重    │
└───────────────┬──────────────────────────────┬───────────────┘
                │ ④a 模型信号（下一步）         │ ④b 安装 / 启用（并行）
                ▼                              ▼
┌─────────────────────────────┐  ┌─────────────────────────────┐
│ ⑤ 模型                       │  │ ⑥ 对话内说明                 │
│   调用新增工具 / 能力        │  │   已安装 / 未安装            │
│                             │  │   本次插件 · 不用时的代价    │
└───────────────┬─────────────┘  └──────────────┬──────────────┘
                │ 工具调用 / Token               │ 用户操作
                └───────────────┬────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ ⑦ 使用与归因账本（install · tool_call · token · 撤销）       │
└──────────────────────────────┬───────────────────────────────┘
                               │ 聚合
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ ⑧ 开发者门户：使用量 · 质量 · token 分成                     │
└──────────────────────────────┬───────────────────────────────┘
                               │ 能力声明 / 版本 / 质量
                               └──────────► 回到 ②
```

按图里的 ②–⑥ 展开。

#### 选什么（②）

分发的单位是能力，不是包名。一个插件可以提供多个能力，一个能力也可以由多个插件提供。用户看到的是「能不能做这件事」，而不是「又一个插件」。

同一套链路不要求插件属于某一类型。按调用发生的工具，在任务里出现，按调用计量；常驻的上下文组件，在冷启、设置或上下文压力点出现，默认按注入或处理的 token 计量；开发者自营的交易插件，在出现交易意图时展示。差异只在触发时机、计量方式和免责边界。

| 层 | 输入 | 方法 | 输出 |
|---|---|---|---|
| L0 画像 | 会话事件、工具、文件、错误 | 规则、关键词、实体映射 | `TaskProfile` |
| L1 召回 | 目录、能力索引 | BM25、标签、能力匹配 | 约 40 条 |
| L2 排序 | 候选、安装状态、兼容性 | 打分、硬过滤 | top 1 |
| L3 门控 | 机会净值 | 授权、信任、预算、去重、TTL | 投递或静默 |
| L4 反馈 | 点击、安装、忽略、撤销 | 本地亲和 | 调整权重 |

```
score = 0.35·文本相关 + 0.20·任务标签 + 0.10·阶段
      + 0.15·质量 + 0.05·新鲜度 + 0.10·反馈 + 0.05·多样性

net = 预期收益 × 置信度 − 打断成本 − 安装成本 − 风险
```

一次只给一张卡，减少选择负担；「换一个」可以看备选。推荐理由写 2–3 句，说明命中什么、为什么适合当前任务、有什么代价。

#### 什么时候问（③）

冷启时用户选择推荐范围和上报方式。推荐范围决定静默还是询问，上报方式决定用量是否离开本机。

静默安装需要同时满足：来源和质量达标、无需重启、没有 postinstall、不涉及数据外发、预算未超、用户没有撤销过该插件、任务仍然活跃。

#### 装完怎么用上（④–⑥）

安装不是终点。安装成功后，宿主追加一条 `developer/message`，告诉模型新增了什么能力、下一步可以直接用。它只追加到会话尾部，不改工具声明，也不重写 system prompt。

安装结果通过 `developer/message` 写进对话，模型在下一步能看到：装了什么、为什么装、是否可以直接用。安装失败也会写“当前没有安装”，不允许把失败说成成功。

DSH 自带的 Chat 会把 `developer/message` 渲染成折叠的 context 行，用户不容易注意到。宿主因此同时在 `conversation.chat.turnTail` 注册一张只读卡片，读取同一个 context 节点，把正文显示在回合末尾；它不额外写会话、不调用模型、不增加 token。

模型自己也会查提供方、找工具。旁路因此观察 `plugin_market` 和带插件关键词的 `web_search` 调用：一旦命中，就把「多索引目录 + npm registry + GitHub 仓库」排序后的 top 候选注入下一步，省掉模型再读目录、比兼容性的几轮。它不注册新工具、不改变工具声明，也不重复模型已经拿到的网页结果。目录支持多个 format-1 索引按包名合并；npm 与 GitHub 按需补目录未收录的包。推荐不依赖插件已经安装：未安装的 npm 包或 GitHub 仓库都可以被推荐，安装前先 `inspect`。静态目录不够强时，普通任务也会先按需扩召回。GitHub 仓库通过 `installSpec` 安装，不声明 `dsh.bundle` 就在预检失败。用户明确选择「全部自动安装」时，安装成功会在回合末尾出现「已自动安装」卡片，写明收益并给出撤销按钮。

最终回复末尾要说明本次安装了哪些插件，以及不用插件时需要多做什么。这样用户看到的不是一张安装卡，而是任务结果的一部分。

### 1.5 Demo：冷启授权 → 推荐 → 安装 → token

这条 demo 用一份病案首页编码记录，把冷启、推荐、安装和 token 账本串起来。冷启是客户端假弹窗，不接官方 onboarding，也不依赖 `consent.json`。

**素材**

- 文件：[record.json](../cases/icd-audit/input/record.json)，一份住院病案首页的编码记录（主要诊断、其他诊断、主要手术操作、入院病情）；
- 目标插件：`dsh-icd-rule-check`（GitHub `PerryLink/dsh-icd-rule-check`，npm 0.2.12）；
- 用例说明：[CASE.md](../cases/icd-audit/CASE.md)；
- query：

```text
这份病案首页的 ICD 编码帮我核一下：诊断和手术编码有没有形式错误、重复、星剑号没配对的地方。
```

**步骤**

1. **冷启授权**。刷新页面，客户端检查本地标记，首次直接弹出授权卡：
   - 安装策略四选一：全部自动安装 / 仅官方精选自动安装 / 始终不自动安装 / 关闭推荐功能；
   - 用量上报二选一：纯本地 / 上报用量，可帮助插件开发者获取收益。

   这一步不写入官方冷启流程。想重看弹窗，清掉浏览器里的 `dsh-plugin-sidekick:onboarded:v2` 再刷新。

2. **发送 query**。旁路读取会话事件，生成任务画像，命中病案编码与质控意图。离线排序验证过：这条 query 的 top1 是 `dsh-icd-rule-check`，分数 0.636，第二名 0.476。

3. **对话内推荐**。宿主追加 `developer/message`，把「推荐/正在安装」和理由写进上下文。模型在思考和回复里能看到，不需要侧栏卡片。

4. **安装**。策略为「全部自动安装」或「仅官方精选」且通过门槛时，宿主走 `inspect` 与 `installBundle`；安装结果再追加一条消息。失败会写“当前没有安装”，不会报成功。策略为「始终不自动安装」时只写推荐。

5. **模型下一步能用**。安装成功后，消息告诉模型新增了 ICD 编码核对能力。模型调用 `icd_rule_check`，拿到一份带条款引用的差异清单——每条发现都带文件名、文号、条款号和逐字摘录，执行不了的检查进 `skipped`。最终回复末尾说明本次装了哪些插件、不用插件时需要多做什么；这里是不用插件时得自己去翻《住院病案首页数据填写质量规范》与医保结算清单填写规范，逐条比对。

6. **token 账本**。`toolOwners` 把 `icd_rule_check` 映射到 `dsh-icd-rule-check`。调用产生的 usage 写入 `usage.json`：

   ```bash
   cat ~/.dsh/plugin-foundry/ledger/usage.jsonl
   ```

   或调用 `report` RPC 拿按插件的聚合。

**检查点**

| 检查点 | 预期 |
|---|---|
| 冷启授权 | 打开即弹出，两组选择，不接官方 onboarding |
| 推荐位置 | 推荐写进对话上下文；回合末尾有可见卡片；不出现侧栏/悬浮卡 |
| 推荐稳定性 | top1 为 `dsh-icd-rule-check`，不是泛化的表格 / 知识库插件 |
| 安装真实性 | 失败写“没有安装”，不会报成功 |
| 模型使用 | 下一步调用 `icd_rule_check`，而不是自己编 ICD 规则 |
| 报告边界 | 未配置对照表的检查进 `skipped`，不报成 error |
| token 归因 | `report` 或 `usage.json` 出现 `dsh-icd-rule-check` |
| 结束总结 | 最终回复说明本次安装的插件，以及不用时的代价 |

**已验证的部分**

- 排序：离线用真实目录跑过，top1 为 `dsh-icd-rule-check`（0.636），第二名 0.476；
- 插件实测：`record.json` 跑出 5 条发现——IC-001 编码形式、IC-007 手术编码形式、IC-002 重复、IC-006 入院病情为 4 的主要诊断、IC-008 主诉无字面呼应；
- 边界行为：材料里有一个没配对的星号编码 `H28.0*`，插件不报 error，而是在 `skipped` 里写“未配置剑号↔星号对照表，无法判断配对是否成立”；
- 报告形态：每条发现带条款引用（国卫办医发〔2016〕24号 第六条 / 第十条 / 第十九条、医保办发〔2020〕20号 附件1），并附免责声明；
- 校验：`python3 cases/icd-audit/verify.py` 12 项通过。

**还没覆盖的部分**

- `toolOwners` 目前是手工映射，换插件要补工具名；后面应从 manifest 自动生成；
- 规则集版本（2026.1）要与编码员所用目录版本一致；插件只核形式与记录内部关系，不查编码目录；
- 材料要 JSON/YAML，Excel 病案首页得先转；转出来的字段仍要人工核对；
- 模型不一定在安装的同一回合调用新插件，必要时补一句「用刚装的 ICD 插件核一下」。

## 2. 计量：按 token 分成

### 2.1 为什么按 token 分成

按 token 分成有几个直接好处：

1. **不需要新的收银台**。用户已经在为模型调用付 token 费用，插件收入从这笔费用里分出来，用户不用再判断「这个插件值不值得单独买」。
2. **按使用付费，门槛低**。插件被调用才产生收入，开发者不用先做订阅系统、试用系统、退款系统。
3. **比按安装量分成更难刷**。安装可以刷，token 消耗要经过模型请求，还要和服务商账单对得上。
4. **和现有计费同轨**。平台不需要发明新的计价单位，财务和对账可以直接复用 token 账单。
5. **适合开源和轻平台**。平台只做计量与结算，不碰商户、税务、退款；开发者想另外收费，可以自己接支付。
6. **对组件型也适用**。注入型按注入 token，压缩/缓存/路由型按处理的 token 计量，不必默认做订阅。

和其他计费方式比，token 分成也省事：按调用次数计费，开发者可以拆调用刷量；按订阅计费，开发者要先做开通、续费、退款；按安装量计费，收入和使用完全脱节。token 分成沿用现有账单，用户不用重新做购买决策，开发者不用先搭收银台，平台也不用处理退款和拒付。

它也有边界：低价插件分到的钱可能很少；节省型插件不能按「省下来的 token」分成，否则省得越多开发者越不赚；平台如果只按 token 分成，会有鼓励多用 token 的倾向，需要用质量门槛、预算和用户选择来约束。

#### 结算方式：分成与返点

token 收益可以有两种结算口径：

| 方式 | 计算 | 给到开发者的形式 | 适用 |
|---|---|---|---|
| 收入分成 | 插件归因的 token 收入 × 分成比例 | 现金或平台余额 | 默认，可提现 |
| Token 返点 | 插件归因的 token 消耗 × 返点比例 | token 配额或抵扣额度 | 开发者继续在平台跑任务 |

返点按消耗量算，不按收入算。例如插件带来 10,000 token 消耗，返点比例 10%，开发者得到 1,000 token 配额。返点不是现金，通常不可提现、有有效期，并受预算和风控约束。

返点适合还在平台上持续开发的团队：它降低试错成本，也把开发者留在生态里。分成适合需要现金收入的开发者。两者可以按开发者或插件配置，但同一笔用量只能选一种结算口径，避免重复支付。

### 2.2 记录

宿主在请求和工具调用结束时写一条用量事件：

```json
{
  "schema": 1,
  "plugin_id": "pkg:npm/dsh-excel-chat@1.2.0#sha256:...",
  "publisher": "ed25519:...",
  "tool": "excel_create_chart",
  "request_id": "session:turn:step",
  "session_hash": "...",
  "tokens": {
    "input": 1200,
    "output": 340,
    "cache_read": 800,
    "cache_write": 0,
    "reasoning": 0
  },
  "share": 0.5,
  "meter_key": "ed25519:...",
  "ts": 1793813045
}
```

事件只记计数和哈希，不记 prompt、文件内容、工具参数。流式请求等最终 usage 到达后再结算，不按 chunk 记。工具到插件的映射优先读 `toolOwners` 配置；没有配置时记为未归因，不猜测归属。

事件先写入本地 append-only 账本，再进入聚合流程。请求路径上不做网络请求。

### 2.3 归因

一次请求可能调用多个插件，归因采用三个不相交的桶：

```
Tokens_p = Σ_r (share_{p,r} × base_tokens_r)
         + tool_result_tokens_p
         + capability_tokens_p
```

- `base_tokens` 是请求的输入和输出，按该请求里的插件工具数均分，或按工具结果大小加权；
- `tool_result_tokens` 是工具返回的内容，归工具提供方；
- `capability_tokens` 是能力信号和回执占用的 token，归对应插件。

三个桶加起来不能超过请求的总 token。超过时按比例缩放，剩余部分不归属任何插件。

最终还有一道对账：某个宿主在一个周期内的归因总量，不得超过模型服务商的实际账单。账单是外部锚点，也是防刷量的最后一道约束。

### 2.4 聚合与上报

本地按日聚合，生成 Merkle 批次。每条事件带 `prev_hash`，形成链式结构，重放或删除都会留下缺口。批次由宿主密钥签名，密钥在安装时生成，存 OS keychain。

默认只上报聚合，不上报原始事件：

```json
{
  "schema": 1,
  "batch_id": "b_20261105_host01_01",
  "host_id": "ed25519:...",
  "install_id": "i_...",
  "runtime_version": "0.2.1-rc.5",
  "period": { "start": "2026-11-04T00:00:00Z", "end": "2026-11-05T00:00:00Z" },
  "root": "sha256:...",
  "prev": "sha256:...",
  "totals": [
    {
      "plugin_id": "pkg:npm/dsh-excel-chat@1.2.0#sha256:...",
      "publisher": "ed25519:...",
      "tokens": { "input": 12000, "output": 3400, "cache_read": 8000 },
      "requests": 42,
      "tool_calls": 37
    }
  ],
  "sig": "ed25519:..."
}
```

传输使用 HTTPS，`POST /v1/usage/batches`，请求体 gzip 或 zstd 压缩。鉴权用安装时注册的 `install_id` 和设备证书。`batch_id` 是幂等键，重复批次返回已有结果。

平台侧按顺序验签、检查 `prev` 链、去重、对账、异常检测、入库，返回 `{accepted, batch_id, server_seq, disputes}`。失败时客户端退避重试；离线时留在 `outbox/`，联网后再发。

### 2.5 纯本地与边界

用户可以关闭上报，只在本地统计：

| 模式 | 上传 | token 分成 | 本地功能 |
|---|---|---|---|
| 纯本地（默认） | 无 | 不参与 | 本地账本、统计、导出可用 |
| 上报用量，可帮助插件开发者获取收益 | 按日聚合，无原文 | 参与 | 同上，另加开发者分成或返点 |
| 审计样本（可选） | 聚合加抽样收据 | 参与 | 用于争议和抽查 |

纯本地模式下不上传、不回填、不后台重试。平台拿不到该用户的用量，开发者也不从其使用中获得分成。用户仍可手动导出报告。

只统计 DSH 内的使用：

- 收据只由 DSH 宿主签发，绑定 `host_id`、`profile_id`、`session_hash`、`request_id`；
- 工具归属来自 DSH 工具注册表或 `toolOwners` 配置，只有经过 DSH 工具管线的调用才计数；
- 插件自报、其他客户端、插件绕过 DSH 直连模型 API 的消耗，都不计入；
- 最终以 DSH 模型服务商的账单为锚，归因总量不得超过实际计费 token。

### 2.6 防滥用：避免开发者故意增加 token 消耗

按 token 分成本质上是按用量付费：插件让一次请求多消耗 token，开发者就多分成。伪造与重放可以靠签名、账本和账单锚点约束；但「真而没用」的 token 不能靠密码学解决。它需要四层：可验证、可封顶、可检测、可追责。

#### 威胁模型

| 手段 | 表现 | 现有边界 | 缺口 |
|---|---|---|---|
| 冗长工具输出 | 工具返回大段 JSON / 日志 / 报告，抬高下一次请求 input | 单请求三桶封顶；账单锚点 | 总量真实，账单不会拦；用户多付 |
| 拆分调用 | 一次工作拆成多次工具调用或子任务 | 每次请求独立计量 | 单请求封顶管不了跨请求 |
| 大工具 schema / 常驻注入 | 工具描述、上下文组件常驻，抬高每次 input | 当前只计量工具结果与能力信号 | schema / 注入尚未计量；组件型口径未定 |
| 破坏缓存 | 让 prompt cache 失效，input 变多、cache_read 变少 | 无 | 需要 cache 命中率异常检测 |
| 伪造 usage | 插件 append 带假 usage 的 assistant/message | 只接受 `source.kind === 'model'`；批次签名；账单锚点 | Host 仍可重签；账单内抢归因难防 |
| 冒领工具归属 | 目录声明别人的工具名，安装后写入本地映射 | 本地 `toolOwners` + 目录 `metadata.tools` | 目录声明未签名，存在冲突与抢归因 |
| 自消费 / 多设备 | 自己或批量设备消耗自己的插件 | 分成 / 返点 < 1；预算与去重 | 免费额度、补贴、返点 > 成本时可套利 |

#### 现有边界

- 单请求：三桶之和不超过请求总量，超出等比缩放，余量记为未归因（§2.3）。
- 账期：归因总量不得超过 provider 账单；超出缩放并记争议（§2.4）。
- 批次：签名、install id、`prev` 链、`batch_id` 幂等、Merkle 根；本地哈希链检测删改。
- 经济：默认分成 30%、返点 10%，都小于 100%；同一笔用量只能选一种口径（§2.1）。
- 用户侧：默认纯本地、默认不自动安装；自动安装有质量、风险、预算、去重；撤销后永久拉黑（§1.4、§2.5）。

这些能挡住「假 token」和「超账单」，但挡不住「真而没用」：开发者每多消耗 1 token，默认分成下开发者得 30%、平台留存 70%、用户付 100%。平台和开发者都从更多消耗中获益，因此平台不能只靠自律做审计。

#### 后续要加的五类机制

1. **每插件、每任务预算**。请求、轮次、任务、日四个层级设上限；超出部分只记成本、不参与分成，或按折扣结算。预算由用户在任务开始时给出，任务结束退回未用额度。

2. **按有用增量结算**。以任务成功、用户接受、安装后使用、未撤销为「有用」信号；先扣除内置路径的基线，只对增量 token 分成。失败、撤销、回退的任务不分成或 clawback。token 只作为成本上限，不作为价值本身。

3. **计量口径封顶**。单次工具结果最多计 `max_result_tokens`；工具 schema 与常驻注入按基线差值和上限计量；缓存命中率异常时降权或标记。组件型插件的注入 token 只计增量，不按全量。

4. **异常检测与抽查**。观察每次调用的输出长度、每轮调用数、重复结果、重试、cache_read 比例；随机审计 `Receipt` 的叶子；发布者风险分；结算 holdback、争议窗口与 clawback。

5. **归属与身份**。工具归属由发布者签名，安装时校验 manifest 并检测同名冲突；只信 DSH 工具管线与真实 model source；设备证明、安装速率限制、k-匿名与自交易检测，约束多设备套利。

#### 原则

- **防伪造靠密码学，防滥用靠计量与治理**。前者可以做强；后者只能做到「有上限、可发现、可追责」，不能证明插件真的有用。
- **用户是唯一付款人**。每插件 token / 费用可见、可设预算、可一键撤销，是最有效的约束。
- **平台不是中立审计者**。平台从 token 消耗中分成，质量门槛、争议处理与独立审计需要外部约束；开放协议和第三方复算可以降低单一平台的自证风险。

## 3. 支付与交易：开发者自营

> **实现状态：本章是设计稿，当前 demo 未实现。** 参考实现的代码与演示只覆盖 §1 分发和 §2 计量（含按用量分配）；开发者收银台、许可证与交易型插件均未落地，删除相关代码后 demo 仍可完整运行。

### 3.1 平台边界

| 收益 | 平台角色 | 资金流 | 责任 |
|---|---|---|---|
| token 分成 | 计量、对账、分成 | 用户 → 平台 → 开发者 | 平台结算 |
| 开发者自收费 | 仅分发 | 用户 → 开发者 | 平台不碰钱、不退款 |
| 开发者自营交易 | 仅分发 | 用户 → 商家/开发者 | 平台不参与、不担保 |

平台只对 token 分成承担结算责任。另外两类由开发者自行处理，平台只提供展示位置和免责声明。

### 3.2 开发者自收费

平台不做商户、不碰资金、不开发票、不处理退款。支付由开发者自带，平台只把用户带到开发者的支付入口。

| 方式 | 做法 | 适合 |
|---|---|---|
| 支付链接 | Stripe Payment Links、Lemon Squeezy、Paddle、Gumroad | 买断、订阅 |
| 许可证 | 开发者签发签名许可证，插件本地或联网校验 | 离线、桌面 |
| 赞助 | GitHub Sponsors、Open Collective、爱发电、Ko-fi | 开源、捐赠 |
| 按需付费 | 用户自愿支付，插件不锁功能 | 工具型、社区型 |
| 外部订阅 | 开发者自己的站点或小程序管理订阅 | 有后端能力的团队 |

Agent 只在用户表达购买意图或插件需要授权时展示入口。它展示链接和价格，不自动支付，不代扣，也不诱导。用户跳转到外部完成支付，插件通过许可证或回调确认权益。平台不代管许可证，不承诺退款、发票和售后。

### 3.3 交易型插件

开发者可以在插件里卖商品或服务。开发者是卖方，平台不是商户，不是担保方，也不参与交易。平台不收取佣金、导购返佣、线索费或服务费，不碰资金，不做托管，不做分账，不开发票，不处理退款，也不审核商品真实性或担保履约。开发者自行负责商户资质、税务、消费者保护和售后。

交易型插件按两类规则展示：

1. 用户设置了显性偏好时，按偏好过滤或排序，例如本地或同城、开源或非营利、价格区间、品牌黑名单、不推荐付费交易插件；
2. 用户没有设置偏好时，全量展示匹配项，按使用人数排序。

不按佣金、客单价或平台偏好排序。每条都带免责声明和商家信息：

```
以下为第三方交易插件，商品或服务由开发者或商家提供。
平台不参与交易，不担保履约，不承担售后与退款责任。
请自行核实商家资质、价格与退换规则后再支付。
```

用户随时可以修改偏好，改完立即生效。

### 3.4 商店的支付基座与开源平台的最小集

应用商店是「平台向第三方数字商品收费」跑得最久、规模最大的样本。开源平台不必复制它们的抽成与商户角色，但可以照抄它们的支付基座：先看苹果、谷歌和同类商店提供了什么，再收敛成最小集。

#### 3.4.1 商店提供了什么

| 能力 | 苹果 App Store | Google Play | 同类商店 |
|---|---|---|---|
| 商品与定价 | App Store Connect：消耗型、非消耗型、订阅、优惠 | Play Console：一次性商品、订阅、优惠 | 小程序商店、Steam 也有商品后台 |
| 付款凭证 | StoreKit 2 签名的 JWS 交易 | purchase token | 都是可校验的付款凭证 |
| 服务端校验 | App Store Server API | Play Developer API | 以服务端为准，客户端回调不算数 |
| 事件与生命周期 | Server Notifications V2：续期、宽限、退款、撤销 | RTDN（Pub/Sub）+ Voided Purchases | 推送加查询，缺一不可 |
| 退款与撤权 | `REFUND` / `REVOKE` | Voided Purchases | 退款不是删记录，是追加撤销 |
| 资金与合规 | 平台做 MoR，抽 15%–30% | 同为 MoR，抽 15%–30% | 平台代收、代税、裁决争议 |

国内的小程序商店（微信、支付宝）与 Steam 结构相同：平台代收、平台裁决退款，差别只在费率与开放程度。

一句话：商店的支付基座 = **报价 + 凭证 + 校验 + 事件 + 撤权**；15%–30% 买的是 MoR（收款、税务、退款裁决），不是这几项技术能力。

#### 3.4.2 开源平台的最小集

开源平台不做 MoR，就不该自建收银台、清算与税务；但「付款之后仍然成立」的部分必须自己提供，否则开发者自收费只是一句免责声明。

| 能力 | 提供什么 | 不做什么 |
|---|---|---|
| `Offer` | manifest 里的报价：价格、币种、周期、退款政策链接 | 目录同步、购物车 |
| `Mandate` | 用户授权：范围、上限、有效期、可撤销 | 替用户付款 |
| `PaymentAdapter` | 接 Stripe / Paddle / x402 等：`verify` / `refund` / `revoke` | 托管资金、清算 |
| `Entitlement` | 收款方或支付网络签名的权益凭证：`order_id`、状态、`revoked_at` | 自建订单中心 |
| `Ledger` | 交易账本：幂等键、对账、争议证据（与用量账本分开） | 税务、发票、退款裁决 |

五件事各解决一个问题：`Offer` 让 Agent 能比价，`Mandate` 让代理购买有边界，`PaymentAdapter` 让渠道可替换，`Entitlement` 让「已付款」可验证，`Ledger` 让重复与退款可追。

AI 把购买入口从商店搜索挪进了对话，于是「谁批准了这笔钱」成了新问题：`Mandate` 因此不是可选项，它是 AI 时代新增的那一项基座能力。

#### 3.4.3 两条边界

1. **钱走开发者的渠道。** DSH 不碰资金、不做商户：买断订阅用 Stripe、Paddle、Lemon Squeezy，按次付费可用 x402 这类 HTTP 原生支付。
2. **协议只加薄薄一层。** `Offer`、`Mandate`、`Entitlement` 进协议，分别可映射到 schema.org Offer、AP2 mandate 与 x402 receipt；`PaymentAdapter` 是接口不是协议。不引入 UCP 这类零售协议：目录、购物车、结账、订单管理都不是 DSH 的场景。代理购买时，`Mandate` 就是模型不能越过的授权边界。

#### 3.4.4 参考

- 苹果：[StoreKit 2](https://developer.apple.com/documentation/storekit)、[App Store Server API](https://developer.apple.com/documentation/appstoreserverapi)、[Server Notifications](https://developer.apple.com/documentation/appstoreservernotifications)；
- 谷歌：[Play Billing](https://developer.android.com/google/play/billing)、[RTDN](https://developer.android.com/google/play/billing/rtdn-reference)、[Developer API](https://developers.google.com/android-publisher)；
- 代理支付：[AP2](https://ap2-protocol.org/)、[x402](https://x402.org/)、[ACP](https://openai.com/index/buy-it-in-chatgpt/)。

## 4. 结论

本文从插件生态的分发与收益问题出发，提出以对话内与工作过程分发、分布式 token 计量、开发者自营支付与交易为支柱的方案。当前实现已经验证冷启授权、推荐、安装回执与 token 账本的基本链路，但方案仍不完整：既有实现层面的不足，也有若干定义可以继续细化，这些同时构成后续工作的方向。

其一，归因粒度仍然较粗。当前以请求为单位记录 token，多插件请求按工具数量或结果大小分摊，`toolOwners` 依赖人工配置。单次工具调用的计量、上下文注入 token 的归属、组件型插件的计量口径，以及未归因部分的处理规则，都还没有形成稳定定义。

其二，推荐依据仍以启发式为主。任务画像来自关键词、文件类型和规则，排序采用加权分数，能够支持单场景 demo，但尚不能说明插件是否真正解决了当前任务。能力匹配的判定标准、推荐理由的生成依据、安装后效果的评估指标，以及误报与撤销反馈如何进入排序，都需要进一步明确。

其三，安装后的使用反馈仍未建立。`developer/message` 只完成单向通知，没有定义插件是否被调用、调用是否解决问题、失败是否回退。安装后使用率、成功率与回退率的采集口径，以及这些指标如何影响后续推荐，是可以继续展开的部分。

其四，协议字段与治理仍停留在示意层面。`UsageEvent`、`Receipt`、`Batch`、`Settlement` 已有字段，但版本协商、发布者身份与吊销、分发者注册和争议处理尚未定义。协议规范、一致性测试与验证器接口，是后续从协议验证走向可运营系统的前提。

其五，按 token 分成的激励仍需约束。当前系统能约束「假 token」与「超账单」，但不能约束「真而没用」的 token：冗长输出、拆分调用、大工具 schema、破坏缓存都会抬高用户账单，而开发者与平台都从更多消耗中获益。后续需要每插件 / 每任务预算、按有用增量结算、计量口径封顶、异常检测与抽查、发布者签名的工具归属，以及结算 holdback / clawback；平台不能只靠自律，需要用户透明账单、独立审计与争议处理。

其六，交易层仍停留在「展示入口」。本文只定义了平台不碰钱、不担保、不做商户，却没有定义付款之后权益如何被校验、续期、撤销与对账。§3.4 的调研表明，应用商店真正提供的不是收银台，而是签名凭证、状态机与退款撤权；但商店那套（以及面向零售的 UCP）对 DSH 太重。后续应走轻方案：钱继续走开发者自带的 Stripe / Paddle / x402，DSH 只提供 `Offer`、`Mandate`、`PaymentAdapter`、`Entitlement`、`Ledger` 五项基座能力，不实现目录、购物车、结账与订单协议。

从研究角度看，本方案的意义在于把「插件分发」从目录检索问题重新表述为任务上下文中的能力匹配问题，把「开发者收益」从安装量或交易抽成重新表述为可归因的 token 使用。其有效性也受这两个转向的限制：归因是估算而非证明，推荐是启发式而非因果判断，协议仍处于雏形。当前证据来自单场景 demo 与合成测试，尚不足以支持生产级结论。后续工作应围绕工具级计量与上下文账本、推荐效果评估、安装后反馈、防滥用与结算风控、交易凭证与权益状态机、协议规范化与多分发者互操作，以及真实任务队列上的对照实验展开。

| 决策 | 备选 | 理由 |
|---|---|---|
| 旁路感知，一次性信号 | 常驻工具、每轮检索 | 常驻工具或每轮检索会把 token 成本固定到每次请求；旁路静默时为零，只在机会命中时追加少量信号，成本和噪声都更低。 |
| 预请求授权 | 逐次确认、完全静默 | 逐次确认摩擦高，完全静默又难以建立信任；预授权把选择前移，范围内静默、范围外询问，兼顾效率与控制。 |
| 回执由 UI 生成 | 模型在回答中说明 | 模型生成回执会占用 token，格式也不稳定；UI 生成回执零 token、字段固定，便于撤销和记录。 |
| 平台不自建收银台 | 平台收银、分账 | 平台收银需要支付牌照、商户资质、税务和退款团队；不自建收银台可以把这些责任留给开发者，平台只做分发。 |
| 交易层做「权益」而非「资金」 | 平台托管订单、代收代付 | 应用商店的经验是：难的不是收银台，而是付款后的状态、撤销与证据。平台不做商户，仍可提供签名凭证与权益状态机，资金由开发者与渠道处理。 |
| 凭证由收款方签名，宿主验签 | 插件自报「已付款」 | 插件运行在用户机器上，自报不可信；由开发者服务端签发、宿主验签，可与 Batch 复用同一套密钥与 canonical JSON。 |
| 支付渠道做成适配器 | 绑定单一渠道或自建收银台 | 苹果、谷歌 2025–2026 年的费率与外部购买规则反复调整；把费率写进协议就是负债，适配器可以替换渠道而不改协议。 |
| 不实现 UCP / ACP 全栈 | 平台实现目录、购物车、结账、订单 | UCP 面向「平台替商家卖货」：DSH 目录已有、购物车不存在、结账在开发者侧。照搬会为不存在的零售场景建一套协议；只借「商家做 MoR」的分工。 |
| 交易凭证以 provider 证明入库 | 自建订单与支付状态 | 支付网络与收银台已经签发可验证凭证；DSH 只验签、存证、撤权，避免自己做清算与对账，也不替任何一方背书。 |
| 交易型按偏好或使用人数展示 | 平台排序、优选 | 平台排序会把交易责任和偏好判断带回平台；按用户偏好或使用人数展示，平台只提供信息，不做价值判断。 |
| 组件型优先按 token 计量 | 默认订阅/买断 | 组件型插件也按 token 计量，避免默认引入订阅系统；订阅/买断保留为开发者可选，不改变平台默认口径。 |
| 底座协议开源 | 私有接口 | 私有接口会把分发锁在单一入口；协议开源后，第三方分发者可以接入并复算计量，官方不容易从底座变成唯一入口。 |
